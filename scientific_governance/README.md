# Scientific authority and deployment controls

Bootstrap implementation, 2026-10-10. **External deployment is incomplete.**
This directory supplies candidate controls for owner review. Its existence does
not make an agent-controlled machine, repository or credential independent.

## Protected objective and roles

[GOAL.md](GOAL.md) records the full-density Bayesian research objective. Current
occupation-law forecast experiments address only part of that objective.
Every qualifying specification must state three propositions: what is shown,
what remains unshown, and why this advances the approved objective. All three
must be reviewed, including the scientific strength of the criterion itself.
`claim_boundaries.json` supplies conditional claim boundaries for all18 gates:
its `demonstrated` fields describe what a properly qualified pass could support,
not the current status of unpassed gates. Canonical gate/state files remain
authoritative for current outcomes; none are promoted by this register.
Exploratory evidence used to design a criterion must be disclosed. A prospective
experiment alone does not establish that its criterion is scientifically useful.

The owner chooses scope and explicitly approves an exact candidate claim. The
implementer proposes code and development tests and cannot approve promotion.
The executor owns the attempted-case ledger and seals evidence. A separate
operator using a separately implemented verifier attempts falsification. The
owner then adjudicates. A second agent on the same machine provides useful
algorithmic review but cannot supply the required independent operator identity.

## Authentication protocol

`authority.py` verifies four detached SSH-signed JSON receipts:

1. `spec.json` — owner-signed predeclaration, before execution;
2. `execution.json` — executor-signed source/environment/archive/attempt ledger;
3. `verification.json` — verifier-signed independent assessment;
4. `approval.json` — owner-signed exact claim and all preceding receipt hashes.

Each has a `.json.sig` sibling. Namespace:
`lorenz-scientific-governance-v1`. The public `allowed_signers` file must be
outside the candidate checkout and contain exactly three distinct keys with
principals `owner`, `executor`, `verifier`. **Never put private keys here.**
No real keys, signatures or approvals have been generated by this implementation.
Tests generate disposable synthetic identities solely in temporary directories.

`validate_spec` defines the machine schema: question, population, competing
hypotheses, exact primary metric, executable acceptance/failure rules, ordered
attempts, data allocation, required artifacts, limitations, three propositions,
exact commit, complete source-tree/environment/config/goal/gate digests, and
timezone-aware approval time. Protocol v1 accepts zero retries and no exclusions.
Each attempt has an ID, argument-vector `command` and `timeout_seconds`. The
runner substitutes `{output}` in arguments with its fresh evidence directory.
Required artifact paths are relative to that directory.

Signatures establish authenticated attestations under provisioned trust roots;
they do not independently prove calculations or operator independence. Timestamp
ordering is checked, but timestamps are assertions by the trusted services.
An external approved-spec registry/time anchor must establish real pre-execution
ordering. Logical ordering in JSON alone cannot establish it.

`check_transition.py` runs from the **base revision**, checking any new PASSED
gate or edit to a previously PASSED record against the signed chain. It binds
scientific criteria, actual config, exact claim, source, producer report and goal.
Existing unmodified G00–G03 records remain historical scoped decisions. They are
not retroactively authenticated or independently qualified by this machinery.

## Deployment and bootstrap — owner actions still required

Owner selected: **separate restricted agent GitHub identity; owner approves from
another device**. The current session still possesses the owner's admin identity.
Therefore the effective separation remains **BLOCKED**, regardless of written
policy or local file permissions.

1. Outside this session, provision a distinct non-admin implementation identity;
   remove owner/admin credentials from its environment. Use no bypass permission.
   Keep final approvals on the owner's other device. No password/key should be
   pasted into chat. Owner and implementation PR author must differ.
2. Owner reviews this bootstrap PR. Main currently requires one latest-push
   approval, code-owner review, resolved conversations, up-to-date `governance`
   check (GitHub Actions app 15368), signed commits, administrator enforcement,
   and prohibits force pushes/deletion. These remote settings were applied and
   read back. CODEOWNERS becomes effective after merge. The agent cannot review
   its own PR. Signed-commit policy must not be bypassed to merge bootstrap.
3. After trusted code is on main, require `scientific-transition` as an additional
   status check. This bootstrap intentionally fails that job because no trusted
   verifier exists in its base. Do not silently convert bootstrap failure to
   successful validation. Have the owner review the bootstrap explicitly.
4. Owner provisions public roots as `LORENZ_SCIENCE_ALLOWED_SIGNERS` in GitHub
   variables and an external service registry. Only public keys belong there.
   The candidate checkout cannot supply accepted roots. An admin-accessible
   variable is insufficient until credential separation is enforced.
5. Prefer an independently administered required workflow/verifier repository.
   The checked-in workflow remains editable through reviewed PRs. Requiring a
   workflow name alone cannot protect against a malicious workflow replacing
   its own check. Protect workflows, acceptance code, goal, CODEOWNERS, gate
   catalogue and tests through owner review and an external policy anchor.
6. Provision execution, verification and immutable archive services outside the
   implementation account. `deployment/runner.service` is an **uninstalled
   template**, not an operational trusted executor. Freeze installed packages,
   service binary/image, filesystem permissions and source read-only. Restrict
   secrets and network. Review all commands; a submitted command can hide
   internal retries, so the outer ledger alone cannot establish attempt honesty.
7. Provision append-only/object-locked storage under an independent identity.
   Upload every required artifact, independently hash it, verify retention and
   restore, and attest the durable URI. `archive.py` verifies sealed bytes and
   creates a fresh local export without overwriting. It claims **local copy
   only**, never WORM, independent storage or remote reproducibility.
8. Keep final evaluation data in a separately administered evaluation service
   inaccessible to developers. Freeze method and grouped-source split first;
   record every access. Only verifier-controlled evaluation may release final
   summaries. Inspected historical tests remain development evidence. Local
   hidden directories or agent-editable permissions cannot enforce this boundary.

Until these controls are externally verified: **no new scientific promotion and
no expensive G04–G06 campaign**. G04 remains the next scientific gate; governance
deployment is an additional operational hold. Engineering and design work remain
permitted. No training, surrogate replacement, posterior transfer or DA is unlocked.

## Evidence tiers and verification

Report five separate levels: SOFTWARE_VERIFIED, NUMERICAL_CONSISTENCY,
SCOPED_CLAIM_SUPPORTED, INDEPENDENT_REPLICATION, APPLICATION_QUALIFIED.
Never infer a higher tier from a lower one. Historical G03 has scoped finite-law
separation support; independent raw reconstruction/trajectory replication and
application qualification remain outstanding. The new `independent_g03.py`
recomputes distances from archived arrays without producer helpers, checks all
sealed payloads, and checks recorded bounds/margins. It does not regenerate the
density reconstruction, reintegrate trajectories or prove continuum bounds.

Development tests are editable. Scientific acceptance code/tests here are
candidate protected controls pending owner-reviewed bootstrap. Independent
adversarial assessment must use an outside-administered copy and try fabricated
values, missing samples, changed thresholds/denominators, wrong hashes, invalid
approvals, leakage and hidden exclusions. Passing internal mutation tests is
engineering evidence, never independent scientific approval.

## Commands and provenance

Fast tests: `python -m pytest -q tests/scientific_governance`.
Historical array audit: `python -m scientific_governance.independent_g03 RUN`.
Verified fresh export: `python -m scientific_governance.archive RUN NEW_ARCHIVE`.
Candidate service runner: `python -m scientific_governance.runner --help`.
Transition check: `python scientific_governance/check_transition.py --base COMMIT
--root CHECKOUT [--allowed-signers EXTERNAL_PUBLIC_ROOTS]`.

`provenance.inventory` hashes **every tracked project file**, records dirty state,
commit, Python/platform and all installed Python packages. Trusted execution
rejects dirty or mismatched source/environment and post-run source mutation.
Untracked runtime dependencies, OS libraries, compiler, hardware, containers and
external data need additional executor capture and isolation; a pip list alone
does not provide a hermetic build. Required raw artifacts and attempted failures
must be retained before an independently signed receipt can be accepted.
